# Team Agent 协作编排实施规范

**状态：** 实施中；核心约束 mutation、replan 与 adoption 状态机已落地，**§7 的 Web 层（成员约束面板、方案比较视图、adoption vote 控件）尚未落地** —— 服务端 `GET /trips/:tripId/plans`、`GET /planning/:tripId/run/latest` 与 adoption vote 路由均已 member-scoped 可用，但前端无挂载点，Shared Agent 的输出对用户不可见。该缺口按 [共享方案面实施规范](shared-plan-surface-implementation.md) 补齐。成员私有对话候选的 batch 生成、确认交接与 Web 接入改按 [成员对话候选到 Shared Agent 交接实施规范](member-conversation-handoff-implementation.md) 实施；该规范取代本文中 owner-only / 人工 form 交互的后续实现约定。
**范围：** 多成员 Personal Agent 向 Shared Trip Agent 的结构化交接、私密约束、自动重规划和方案采用投票。
**事实来源：** `TECH_STACK.md`、`docs/PRD.md`、`docs/backlog.md`、`docs/test-scenarios.md`、`docs/agent-architecture.md` 与本文件。若本文件与旧的长期记忆实施细节冲突，以本文件为准。

## 1. 固定决策与不变量

1. Personal Agent 可以从 owner 的私有 Profile、当前 Trip override 和有界私有对话中**生成结构化候选提案**；它不能自动确认、自动共享或直接写入 Shared Agent 输入。
2. 每个被确认的 Trip 约束必须声明 `visibility`：`TEAM_VISIBLE` 或 `ORCHESTRATOR_CONFIDENTIAL`。未确认的提案和 `PRIVATE` 数据永不进入 snapshot。
3. `TEAM_VISIBLE` 对当前 active members 与 Shared Agent 可见；`ORCHESTRATOR_CONFIDENTIAL` 只对 owner、服务端 projection builder 和 Shared Agent 的本次 planning/replan prompt 可见，不出现在其他成员的 API、UI、plan explanation、audit、SSE、日志、trace 或 metrics。
4. `ORCHESTRATOR_CONFIDENTIAL` 不是“不可推断”承诺：方案选择可能间接反映某个私密约束。确认 UI 必须说明这一残余风险；系统不得显示具体值、成员归属或由该值生成的自由文本理由。
5. Shared Agent 不读 `chat_threads`、`chat_messages`、`user_profiles`、`preference_facts` 或 proposal 表。它只消费本次 immutable snapshot 和当前 run 的规范化 provider evidence。
6. 约束分为 `HARD` 与 `SOFT`。HARD 约束不能由模型静默放宽；无可行方案时返回结构化阻塞项。SOFT 约束只能用于排序和解释。
7. 任何有效 consent、已确认 Trip fact、个人事实投影源、价格、库存或成员资格变化，必须在同一事务中令旧 ACTIVE plan 及其 confirmations 为 `STALE`，并自动 enqueue `REPLAN`。旧 plan 仅可查看、比较和审计，永不恢复为可确认或可预订状态。
8. 自动 replan 产生 `PROPOSED` plan。所有 required members 投票 `ACCEPT` 后才转为 `ACTIVE`；任一 `NEEDS_CHANGES` 阻止采用并保留 proposal 供比较。ACTIVE 后仍须按既有确认流程由全部 required members 对同一版本显式确认，才可调用 booking sandbox。
9. PostgreSQL、服务端事务和版本条件更新是唯一业务真相。LLM、浏览器状态、SSE 和 provider 返回均不能改变上述不变量。

## 2. 复用的系统架构

继续使用现有技术栈：Next.js/React/TypeScript + TanStack Query，Fastify API，PostgreSQL/RDS + Drizzle migrations，持久 `agent_task_runs` Worker、PostgreSQL lease、transactional outbox、受限 Skill Registry、ModelGateway、OpenTelemetry/Pino 和鉴权 fetch SSE。不得为本功能引入自由 Agent-to-Agent 协议、Redis、Kafka、Temporal、Step Functions、WebSocket、向量数据库或 RAG。

```text
owner private thread/Profile
  -> Personal Agent: typed constraint proposal only
  -> owner confirm + select visibility/strength
  -> TripFactService transaction
       -> trip_constraint_facts revision
       -> stale active plan/confirmations
       -> outbox: REPLAN requested
  -> Planning acceptance: MemoryProjectionBuilder
       -> immutable constraint_snapshot
  -> durable Shared PLAN/REPLAN Worker
       -> candidate research matrix for every configured destination
       -> Shared Agent synthesis + deterministic validator
       -> PROPOSED plan
  -> required-member adoption votes
       -> ACTIVE plan -> existing booking confirmations -> sandbox
```

## 3. 数据模型与迁移

所有值表均只保留结构化、allow-listed 数据；不写入私聊原文、模型 prompt/response、passport number 或其他未授权敏感字段。

### 3.1 枚举

```sql
CREATE TYPE constraint_visibility AS ENUM (
  'TEAM_VISIBLE',
  'ORCHESTRATOR_CONFIDENTIAL'
);
CREATE TYPE constraint_strength AS ENUM ('HARD', 'SOFT');
CREATE TYPE constraint_proposal_status AS ENUM (
  'PENDING', 'CONFIRMED', 'DISMISSED', 'REVOKED'
);
ALTER TYPE plan_status ADD VALUE IF NOT EXISTS 'PROPOSED';
CREATE TYPE plan_adoption_decision AS ENUM ('ACCEPT', 'NEEDS_CHANGES');
```

Existing PostgreSQL enum migrations must use the repository's versioned migration convention; do not recreate existing enum types on upgrade databases.

### 3.2 `trip_constraint_proposals`

Private, owner-reviewable candidate generated by a Personal Agent or a structured owner command.

| Column | Requirement |
|---|---|
| `id`, `trip_id`, `owner_user_id` | UUID foreign keys; owner must be an active member. |
| `field_key`, `value_json`, `value_hash` | fixed field catalog + strict Zod value schema; hash is for idempotency/dedup, never telemetry. |
| `strength` | requested `HARD` or `SOFT`; sensitive catalog entries may restrict allowed strength. |
| `proposed_visibility` | user-selectable default only; not authoritative until confirm. |
| `source_kind` | `PERSONAL_AGENT` or `OWNER_FORM`; no raw-chat reference/body. |
| `status`, `created_at`, `resolved_at` | lifecycle; only `PENDING` may be confirmed/dismissed. |

Unique partial index: `(trip_id, owner_user_id, field_key, value_hash)` where `status='PENDING'`.

### 3.3 `trip_constraint_facts`

The current Trip-scoped authoritative contribution. It replaces the general `PERSONAL_OVERRIDE` shape when the fact can affect Shared planning.

| Column | Requirement |
|---|---|
| `id`, `trip_id`, `owner_user_id` | FK; one fact belongs to one Trip and one owner. |
| `field_key`, `value_json`, `value_hash`, `strength`, `visibility` | validated against the field catalog. |
| `revision` | monotonic per `(trip_id, owner_user_id, field_key)`; no in-place value mutation. |
| `source_proposal_id` | nullable FK; records owner-approved origin without retaining chat text. |
| `status` | `ACTIVE`, `SUPERSEDED`, `REVOKED`; partial unique active index per owner/trip/field. |
| `created_at`, `superseded_at`, `revoked_at` | auditable lifecycle timestamps. |

Only `TEAM_VISIBLE` facts appear in member-facing workspace payloads. Both approved visibility modes may be included in the internal snapshot projection according to the active consent policy. For `PERSONAL_AGENT` profile-derived values, an active Trip-scoped grant whose `field_list` contains the exact catalog key remains mandatory. `OWNER_FORM` is an explicit direct Trip command and does not claim to read a Profile field.

### 3.4 Snapshot projection manifest

Do not expose a separate read API for confidential data. Extend `constraint_snapshots.authorized_data` to a versioned, server-internal projection:

```ts
type ConstraintSnapshotData = {
  schemaVersion: 2;
  teamVisible: Record<MemberAlias, ProjectedConstraint[]>;
  orchestratorConfidential: Record<MemberAlias, ProjectedConstraint[]>;
  projectionManifest: Array<{
    sourceType: 'PROFILE_CONSENT' | 'TRIP_FACT';
    sourceId: string;
    revision: number;
    visibility: 'TEAM_VISIBLE' | 'ORCHESTRATOR_CONFIDENTIAL';
  }>;
  departureCities: string[];
  destinationCandidates: string[];
  travelDateStart?: string;
  travelDateEnd?: string;
};
```

`MemberAlias` is a run-scoped opaque alias. The model never needs user IDs for confidential constraints. The API maps eligible member-specific tasks back to users only after validation. Snapshot rows are historical records and are never rewritten on revoke; they are simply invalid for future execution.

### 3.5 Plan adoption votes

Add `plan_adoption_votes(plan_id, user_id, decision, created_at, updated_at)` with unique `(plan_id, user_id)`. It is separate from existing `member_confirmations`: votes decide whether a `PROPOSED` replan becomes `ACTIVE`; confirmations authorize sandbox booking only after activation.

## 4. Field catalog and policy enforcement

Create `src/policy/constraint-field-catalog.ts` as the single allow-list. Each entry declares JSON schema, sensitivity, allowed visibility, allowed strength, whether profile consent is required, and the safe public explanation token.

Initial catalog:

| Field | Strength | Visibility | Notes |
|---|---|---|---|
| `departure_city`, `travel_date_window` | HARD | TEAM_VISIBLE | existing Trip brief fields remain server-authoritative. |
| `budget_max`, `accessibility_need`, `special_schedule_limit` | 当前仅 SOFT | TEAM_VISIBLE or ORCHESTRATOR_CONFIDENTIAL | 当前 evidence 无法确定性证明个人预算分摊、无障碍或自由文本日程；不得伪装为 HARD。 |
| `no_red_eye`, `accommodation_style`, `travel_pace`, `interests` | `no_red_eye` 可 HARD；其余 SOFT | both modes if catalog permits | `no_red_eye` 由服务端按选中航段 ISO 出发本地时刻（22:00–05:59 为红眼）验证；模型不得自行豁免。 |
| nationality/travel document | not proposal-eligible | existing dedicated consent only | form-only; no Personal Agent extraction. |

`ConstraintProposalService` and `TripConstraintFactService` must parse catalog schemas server-side. The client and model may select a key/value only; they cannot create catalog entries, use arbitrary JSON, assign another owner, or bypass visibility rules.

## 5. Service and Agent contracts

### 5.1 Personal Agent

Add `trip.constraint.propose` Personal Skill:

```ts
input: { tripId: UUID; question: string; threadContext: bounded owner-only context }
output: { proposals: Array<{
  fieldKey: CatalogKey; value: JsonValue; strength: 'HARD' | 'SOFT';
  suggestedVisibility: 'TEAM_VISIBLE' | 'ORCHESTRATOR_CONFIDENTIAL';
  safeRationale: string;
}> }
```

The output is validated by catalog schema and stored only as `PENDING` proposal. The skill has no `snapshot:read`, `plan:write:propose`, direct database or Shared Agent tool scope. `safeRationale` is owner-only and must not quote prior chat.

### 5.2 Commands and reads

All commands require authenticated active membership, a required UUID idempotency key and a transaction. Request/response schemas are strict Zod and must be added to OpenAPI. The server derives snapshot IDs, preference versions and REPLAN request IDs; clients must never supply those internal authorities.

| Endpoint | Behavior |
|---|---|
| `POST /trips/:tripId/constraint-proposals` | Owner creates a form-origin proposal; Personal Agent-created proposals use an internal service call, not a model-write endpoint. |
| `GET /trips/:tripId/constraint-proposals/me` | Owner reads only own pending/resolved proposals. |
| `POST /trips/:tripId/constraint-proposals/:proposalId/confirm` | Owner supplies final `visibility` and `strength`; locks proposal and Trip, writes/replaces active fact, stales old plan, enqueues REPLAN. |
| `POST /trips/:tripId/constraint-proposals/:proposalId/dismiss` | Owner-only terminal dismissal; no stale/replan. |
| `PUT /trips/:tripId/constraints/:factId` | Owner replaces an active fact through a new revision; same stale/replan transaction. |
| `DELETE /trips/:tripId/constraints/:factId` | Owner revokes fact; same stale/replan transaction. |
| `GET /trips/:tripId/constraints/me` | Owner's own facts including confidential values. |
| `GET /trips/:tripId/constraints` | Members receive TEAM_VISIBLE facts only. |
| `POST /plans/:planId/adoption-votes` | Required member sets `ACCEPT` or `NEEDS_CHANGES` for a current `PROPOSED` plan. |
| `GET /trips/:tripId/plans` | Members get old STALE plan as reference and latest proposed/active plan; confidential values never serialize. |

### 5.3 Transactional mutation flow

For confirm, replace, revoke, consent mutation, profile projection-source mutation and membership removal:

1. lock the Trip and target fact/proposal rows;
2. validate actor ownership/membership, field catalog and optimistic revision;
3. write the new immutable revision or terminal state;
4. call the common stale function for all ACTIVE plans and booking confirmations;
5. cancel/supersede any active planning task safely, create a new immutable snapshot and enqueue one `REPLAN` task with outbox event;
6. write value-free audit event and return the durable run ID.

The mutation must fail atomically when the Trip has no required member or no confirmed flight-search preference. It must not commit a new fact after staling a plan unless it can also create the immutable snapshot and accept the replacement `REPLAN` run.

The new snapshot must be created inside the acceptance transaction after all fact writes. Its manifest is pinned to `agent_task_runs`; finalization checks that the task lease, snapshot ID, member set and projection manifest are still current. A changed source makes the task terminal `STALE` and prevents any plan write.

## 6. Shared planning, proposal, and adoption state

### 6.1 Research and synthesis

The planning worker must build a research matrix for every `(origin, destinationCandidate, service)` combination before synthesis. `Promise.allSettled` is permitted only behind configured concurrency limits and per-provider deadlines. Missing data is represented as `UNAVAILABLE`, never fixture fallback.

The Shared Agent receives a model-only projection containing `teamVisible` plus `orchestratorConfidential` snapshot sections and evidence IDs. It never receives the legacy user-ID keyed `authorized_data` map or server-only userId-to-alias lookup. It may use all constraints for optimization. The deterministic validator must enforce:

- all configured destination candidates are represented;
- every selected provider item exactly matches current run evidence;
- every constraint reference appears in the snapshot manifest;
- no HARD constraint is silently waived;
- output contains no confidential value, source ID, member alias or free-form explanation derived from confidential data.

For public explanation, the model returns allow-listed explanation tokens such as `SATISFIES_ALL_PRIVATE_CONSTRAINTS`; the server renders localized fixed text. It must not generate a narrative about confidential constraints.

### 6.2 Plan lifecycle

```text
ACTIVE --(source/provider/member change)--> STALE
STALE --(auto REPLAN)--> remains reference-only
REPLAN succeeds --> PROPOSED
PROPOSED --(all required ACCEPT)--> ACTIVE
PROPOSED --(any NEEDS_CHANGES)--> PROPOSED / next REPLAN
ACTIVE --(all existing booking confirmations)--> booking sandbox eligible
```

Only a plan whose snapshot remains valid may become `PROPOSED`. An old plan is never restored. If a new fact changes while voting is in progress, the proposed plan becomes `STALE`, its votes are invalidated and the latest REPLAN supersedes it.

## 7. Web implementation

Add to the Trip workspace:

1. Personal private-thread proposal cards with field, value, strength, visibility selector, residual-inference warning and confirm/dismiss actions.
2. A member-facing constraints panel showing only `TEAM_VISIBLE` facts and source category, never confidential facts or count-derived disclosure.
3. A plan comparison view with prior `STALE` version, current `PROPOSED` version, provider evidence freshness and safe change reasons.
4. Adoption vote controls for required members. The UI must distinguish adoption vote from booking confirmation and state that the old plan cannot be restored.
5. Query invalidation after every accepted command for trip, constraints, plans, votes and agent-run keys. SSE only updates safe phase/status; all results rehydrate from REST.

No raw snapshot, confidential fact, model rationale, message history or vote authority may be placed in browser storage or a global client store.

**实施归属：** 第 1 项由 [成员对话候选到 Shared Agent 交接实施规范](member-conversation-handoff-implementation.md) 实现（成员私聊内的候选卡）。第 2–5 项由 [共享方案面实施规范](shared-plan-surface-implementation.md) 实现：它们统一落在 Trip workspace 对话侧栏顶部的一个**只读、trip 内全体 active member 可见**的共享方案面上，而不是分散到 inspector。该面不接受任何成员写入的消息，不创建共享 `chat_thread`，因此不构成 `docs/PRD.md` 非目标中的原生群聊，也不为 Shared Agent 开放聊天入口。

## 8. Observability, security, and deletion

Add value-free audit actions: `TRIP_CONSTRAINT_PROPOSED`, `TRIP_CONSTRAINT_CONFIRMED`, `TRIP_CONSTRAINT_REVOKED`, `PLAN_REPLAN_ENQUEUED`, `PLAN_ADOPTION_VOTED`, `PLAN_ADOPTED`. Audit summaries may contain scope/visibility/strength enums, field category, outcome, revision and correlation references; never value, member alias, source ID, text or hash.

Add low-cardinality metrics: `trip_constraint_mutation_total{operation,visibility,strength,result}`, `plan_adoption_vote_total{decision,result}`, `plan_replan_total{trigger,result}`. IDs and field values are forbidden labels. Add spans `trip.constraint.mutate`, `snapshot.projection.build`, `plan.adoption.vote` with the same bounded attributes.

If an owner deletes/revokes a confidential fact, remove its active value record, stale all dependent nonterminal plans and prevent future projection. Historical immutable snapshots/plans remain audit records but cannot be exported to a new run or member response. Encrypted RDS storage and existing secret/log redaction controls apply; no new provider key or client configuration is introduced.

## 10. Required verification

Add unit, integration and E2E coverage for:

1. Personal Agent proposal cannot create a fact without owner confirmation.
2. A confidential budget is available to the Shared planning prompt but absent from every other member API/UI response, plan JSON, explanation, audit, SSE, log, trace and metric label.
3. A team-visible fact is visible only to active members of that Trip; neither cross-Trip nor non-member reads succeed.
4. HARD constraint conflict produces a structured blocking result; SOFT conflict changes ranking only.
5. Confirm/revoke/update and consent/profile changes atomically stale old plans, confirmations, proposed-plan votes and in-flight tasks, then enqueue exactly one idempotent replan.
6. Research covers every configured candidate and required origin; provider failure remains `UNAVAILABLE`.
7. Replan creates `PROPOSED`; a single `NEEDS_CHANGES` prevents activation; concurrent votes create at most one ACTIVE plan; old STALE plans never reactivate.
8. Booking sandbox rejects `PROPOSED`, `STALE`, superseded, non-unanimous and invalid-snapshot plans.
9. Existing owner-only private-thread, context-boundary, cancellation, lease recovery, callback idempotency and telemetry-redaction regressions remain green.

Run `apps/api` `npm run typecheck`, `npm run lint`, `npm test`, `npm run docs:verify`; run equivalent web typecheck, lint and tests after UI changes.

## 11. Risks and implementation notes

| Risk | Required mitigation |
|---|---|
| Confidential constraint inferred from plan outcome | disclose residual risk before confirmation; suppress values/owner identity; use fixed public explanation tokens. |
| Model leaks confidential prompt content | segregated projection sections, opaque aliases, strict output schema, deterministic validator, redaction regression tests. |
| Concurrent mutation/replan/vote activates wrong version | Trip lock, snapshot manifest revision guard, partial unique active-task/active-plan indexes, lease-conditional finalization. |
| Auto replan creates task storms | idempotency key derived from transaction change ID; coalesce/supersede active replan using current task repository semantics. |
| Users confuse adoption and booking confirmation | separate states, endpoints, UI labels and tests; no booking action for `PROPOSED`. |
| Scope grows into hidden multi-agent chat | do not add Shared `chat:read`, raw transcript export, A2A messaging or autonomous tool loops. |

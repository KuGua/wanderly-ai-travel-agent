# Frontend i18n — English default + Simplified Chinese

The Wanderly frontend supports English (`en`, default) and Simplified Chinese (`zh`) via `next-intl` 4.x. Locale is part of the URL: `/en/home`, `/zh/home`. The locale switcher in the sidebar top right swaps locales in place and persists the choice via the `NEXT_LOCALE` cookie that `next-intl`'s middleware sets.

## Routing shape

- All app routes live under `apps/web/src/app/[locale]/`. The `locale` segment is part of `localePrefix: "always"`, so every URL is explicit about its language (`/en/profile`, `/zh/profile`).
- The root `apps/web/src/app/layout.tsx` is a thin pass-through that delegates `<html>`/`<body>` to the `[locale]/layout.tsx`, where `lang={locale}` is set and the `NextIntlClientProvider` wraps the tree.
- `apps/web/proxy.ts` (Next 16 renamed `middleware.ts` to `proxy.ts`) exports `createMiddleware(routing)` from `next-intl/middleware`. This handles locale detection, redirects from `/foo` to `/en/foo`, and the cookie write when the user switches.
- `apps/web/next.config.ts` wraps the config with `createNextIntlPlugin("./src/i18n/request.ts")`. The plugin compiles `messages/${locale}.json` references at build time.
- `apps/web/src/i18n/routing.ts` defines the `defineRouting({ locales: ["en", "zh"], defaultLocale: "en", localePrefix: "always" })` config plus the `Locale` type.
- `apps/web/src/i18n/request.ts` is the `getRequestConfig` callback that loads `messages/${locale}.json` per request.
- `apps/web/src/i18n/navigation.ts` re-exports `createNavigation(routing)` for client-side `Link`, `useRouter`, `usePathname`, etc. Components import from `@/i18n/navigation`, never `next/navigation` or `next/link` directly.
- That rule is enforced by `no-restricted-imports` in `apps/web/eslint.config.mjs`, not by convention. A bare `next/link` href has no locale segment, so the proxy has to redirect and a reader whose locale is not `defaultLocale` can land on the English copy of the page they clicked from — `PinnedResultCard` shipped that way and sent Chinese readers to the English planning-run detail page. The unit-test stub for `next-intl/navigation` renders `href` verbatim, so no component test can catch this; the lint rule is the guard.

## Message catalogs

- `apps/web/messages/en.json` — English (default).
- `apps/web/messages/zh.json` — Simplified Chinese.

Namespaces:

- `common` — page metadata, nav, app-shell chrome, demo badge, error-state defaults, loading strings, units (`km`, `coordinate`).
- `home` — dashboard, profile/trips sections, trip status & accommodation enums, date range & member plurals.
- `profile` — page chrome, sections, field labels/hints/placeholders, accommodation options, validation messages, sticky notes, save affordances.
- `explore` — header chrome, help/unavailable panels, picker panel, pins manager, drawer, kind badges, geography labels, marker aria labels, state machine (`state.*`, `action.*`), layer panel, destination fixtures.
- `trips` — placeholder workspace strings.
- `errors` — `unauthorized`, `generic`, `networkUnreachable`, `invalidResponse`, plus `byStatusCode` mapping for `{401,403,404,409,422,500,502,503,fallback}`.

ICU pluralization is used where the count affects the word (`{count, plural, one {# private pin} other {# private pins}}`). Date/time formatting goes through `useFormatter().dateTime`; the `50 km` unit goes through `Intl.NumberFormat({style:"unit", unit:"kilometer"})`.

## What is and isn't translated

Locale-invariant (kept identical across `en` and `zh`):

- Brand glyphs: `Wanderly`, `W.`, `Wanderly AI`.
- URL segments, ISO date format `YYYY-MM-DD`, separators (`→`, `+`, `·`, `–`, `—`, `…`, `°`), currency code `USD`, `km` glyph.
- Geographic fixture names: `Tokyo`, `Lisbon`, `Reykjavík` — destination catalog keys render verbatim in both languages. Map tile labels from OpenMapTiles still prefer `name:zh` when present (existing `preferredName` logic in `map-geography-layers.ts`).
- `interestsPlaceholder: "art, museums, local food"` and `availableDepartureDatesPlaceholder: "2026-10-03, 2026-10-10"` — kept as format examples.

Translated via `messages/*.json`:

- All nav, page chrome, form labels/hints/descriptions, validation messages, error messages, pin state machine, layer panel copy, accommodation style enum, trip status enum.
- Profile fixture display values: per-locale variants live in `lib/fixtures/profiles.zh.ts` (`旅行者`, `旧金山`, `["艺术","博物馆","当地美食"]`).
- Trip fixture names: per-locale variants live in `lib/fixtures/trips.zh.ts` (`亚洲之旅`, `东京`, `曼谷`, `首尔`).

Server-supplied error messages (the `apiErrorResponseSchema.message` payload) are mapped on the client via `useErrorMessage()` in [apps/web/src/lib/api/use-error-message.ts](apps/web/src/lib/api/use-error-message.ts) using `errors.byStatusCode.*`. The original server message is not surfaced to users; future work is to send `Accept-Language` from `ApiClient` so the backend can localize directly.

## Per-locale fixtures

- `apps/web/src/lib/fixtures/profiles.ts` (English) and `apps/web/src/lib/fixtures/profiles.zh.ts` (Chinese).
- `apps/web/src/lib/fixtures/trips.ts` (English) and `apps/web/src/lib/fixtures/trips.zh.ts` (Chinese).
- `apps/web/src/lib/fixtures/index.ts` exports `useLocalizedProfileFixture()` / `useLocalizedTripsFixture()` hooks that read `useLocale()` and return the right fixture.

Wire-format fields (UUIDs, ISO timestamps, currency codes, enums) stay identical between the two files.

## Deferred / future slices

- Send `Accept-Language` from `ApiClient` so the backend can localize `apiErrorResponseSchema.message` directly. Today, the client maps `TravelApiError.statusCode` to a localized string.
- Localize user-supplied `interests` strings — they currently pass through verbatim.
- Additional locales and RTL support (e.g., `ar`, `he`).
- `next-intl`'s extractor / `@formatjs/cli` for in-source ICU message extraction.
- `useFormatter().dateTimeRange` for `trip.dates.range` if we add ICU `dateTimeRange` formatting.

# 前端 UI 方案与推荐技术栈

**状态：** Hackathon MVP 实施方案  
**范围：** 登录后的 Web/PWA 体验；公开营销页不属于 Hero 路径。

## 1. 产品与界面决策

认证后的首屏是**个人旅行工作台**，不是宣传落地页。它按以下顺序回答用户的问题：

1. 我现在是否需要处理某项旅行事项？
2. 当前行程中哪些信息是私密的，哪些已经共享？
3. Shared Trip Agent 推荐什么，为什么？
4. 团队确认当前方案前，我还需要完成什么？

视觉参考见 [`assets/reference-homepage.html`](../assets/reference-homepage.html)。该文件仅为静态示意；生产实现以本方案中的路由和数据源为准。

### 体验原则

- **行动优先：** 过期方案、未完成授权、待确认、供应商故障、入境核验不确定性优先于普通旅行内容。
- **隐私可见：** 共享字段需标明成员与来源；私密数据绝不能出现在共享卡片、解释或遥测中。
- **证据随附：** 每个旅行或准备事项都显示来源与采集/核验时间；无数据时显示 `UNAVAILABLE` 和恢复路径。
- **不静默替换：** 价格、授权或可用性变化后，方案显示 `STALE`，保留旧/新差异并要求复核。
- **人工确认是硬边界：** 预订页始终展示 `No automatic charge`；除非服务器确认全员已确认当前版本，否则不得显示可用执行操作。

## 3. 首页策略：行程控制台 + 探索地图

首页不应在“热门目的地”和“当前旅行计划”之间二选一。采用双层信息架构：用户先看到不能错过的行程行动，再探索下一段旅行。这样既保留旅行产品应有的发现感，也不会把已过期方案、授权或确认任务藏进地图中。

### 首屏优先级

1. **行动横幅（条件显示）：** 当前用户存在 `STALE` 方案、待完成授权、准备事项或确认请求时，页首显示一张紧凑的行动卡，提供一个明确的下一步链接。
2. **探索地图：** 首页的主要视觉区域。用户通过四个视图发现旅行灵感和自身旅行状态：`为你推荐`、`热门目的地`、`规划中`、`我的足迹`。
3. **当前行程与个人待办：** 地图下方保留当前行程、个人任务与私密偏好摘要，作为完成任务和继续规划的稳定入口。

没有进行中行程或行动任务时，探索地图上移为首屏核心，并显示“开始规划”的明确入口。

### 地图视图与数据边界

| 视图 | 展示内容 | 数据来源 | 隐私规则 |
|---|---|---|---|
| `为你推荐` | 最多 6 个符合用户兴趣、节奏、预算偏好的目的地 | 当前用户的私密 Profile 与其明确保存的偏好 | 仅当前用户可见；解释只引用本人资料。 |
| `热门目的地` | 近期热门或编辑精选地点 | MVP 使用版本化 fixture；未来接入经审核的趋势数据源 | 必须显示 `Demo data` 或来源与更新时间；不可伪装为实时热度。 |
| `规划中` | 当前用户所属行程的候选目的地与已选目的地 | 服务端权威 trip/plan 数据 | 仅显示当前用户有权查看的行程与授权后摘要；不暴露其他成员私密约束。 |
| `我的足迹` | 用户主动保存的历史到访地点 | 当前用户 Profile/历史数据 | 默认私密；不自动用于共享行程。 |

任何地点说明均不得写入或暗示其他成员未授权的资料。例如，使用“符合已授权的团队预算与出发限制”，而不是披露某位成员的具体预算或国籍。

### 交互与视觉方向

- MVP 使用**轻量 2.5D 地图**：支持点选、有限缩放和地点聚焦，但不以自由旋转的 3D 地球作为完成任务的前提。
- 视觉采用浅暖背景、深海蓝地图、琥珀色热门标记、青绿色推荐标记；所有标记同时提供图标、文字和状态，不能只靠颜色区分。
- 用户点选地图标记后打开地点详情抽屉：展示地点图片/摘要、所属视图、匹配原因或来源、数据时间，以及 `查看候选方案` 或 `开始规划` 操作。
- `规划中` 地点以明确文字状态（如“方案 v2，等待复核”）呈现；标记点击与卡片链接到对应 trip/plan 路由。
- 不采用 Google Earth 嵌入、品牌或数据。当前探索页使用 OpenFreeMap + MapLibre globe，并在矢量细节下叠加 GEBCO 官方 WMS 的 public-domain 全球海陆 shaded relief；GEBCO attribution 必须保留且不得用于航海或安全判断。洲、国家、首都/主要城市和省州名称由来源化、版本化的本地 SVG 覆盖层渐进显示，只作为地图参考，不构成目的地、报价、库存、签证或预订事实。若样式不兼容，控制组仍可见但被禁用，并以 `role="status"` 文案说明缺失项（缺 source 或缺图层），保留候选地点入口和地图失败回退；不得静默隐藏以免开发期误判"功能未实现"。
- 地图实现必须延迟加载、预留稳定容器空间以避免 CLS；网络慢、设备性能有限或 `prefers-reduced-motion` 时，回退为静态地图与可访问地点卡片列表。

### MVP 实施阶段

1. 使用静态 SVG 或轻量地图底图、fixture 地点和四类标记验证信息架构；不依赖实时热点数据。
2. 加入四个视图切换、地点详情抽屉、推荐原因及通向行程创建/方案详情的深链接。
3. 用事件验证“查看地点 → 开始规划 / 查看方案”的转化；仅在地图显著改善发现与规划进入率后，评估真实地图引擎与 globe 增强。

   **同阶段强化（§5.2 / §5.2.2 hardening）**：与第 3 步同阶段落地，将 layer panel 的"style 不兼容即隐藏"改为"始终渲染 + 禁用 + caption"，并通过 `window.__wanderlyMap` 给开发者暴露 5 种 readiness（见 `docs/frontend-prototype-handoff.md §5.2.2`）；fixture 由 `apps/web/src/components/explore/__fixtures__/openfreemap-liberty-layers.ts` 固化并与 `GEOGRAPHY_LAYER_IDS` 在测试时做交集校验，捕捉 Liberty 升级或 style URL 变更引起的 layer 漂移。

验收时，键盘用户可在视图切换、标记列表和地点抽屉间完整操作；每个交互目标至少 44px，地图状态有文字替代，且页面在地图尚未加载时仍可进入当前行程和待办。

## 4. 页面规格

### 会话入口与演示用户切换 — P0

Hackathon 期间仅使用现有 `X-Demo-User` header。页面必须清楚显示当前身份；身份切换时清空缓存的服务端数据；不能暗示这是生产认证。提供 Alice、Bob、Chen 三个独立选项，且不得用会持久化或泄漏的 URL query 表示用户选择。

### 个人工作台 — P0

包括：需处理的过期方案/待授权/缺失数据/确认请求卡片；当前用户的行程列表（私有草稿与共享行程分开）；标有快捷提示的私有 Personal Agent 面板及未来文本输入；规划复核、准备核验、授权完成和确认等个人待办；偏好摘要（`Profile`、`This trip`、`Shared for this trip`）；以及跳转至授权管理的范围化共享提示。

此页绝不显示其他成员未共享的偏好、国籍、证件资料或私有对话。

### 私密资料与单次覆盖 — P0

表单按航班偏好、住宿/节奏/兴趣、预算、旅行限制分组。每项已保存资料显示来源和最后更新时间。删除必须有确认对话框；单次覆盖应明显区别于可复用资料，`Save to profile` 只能是独立的确认动作。

### 创建、邀请与加入 — P0

MVP 仅允许两个出发地、两个或三个 fixture 候选目的地及已注册成员。创建流程采用渐进展开：行程基本信息 → 成员 → 路线/候选设置 → 复核。行程工作区的创建者在“行程概览”上方可按显示名称搜索可邀请账号；搜索结果只返回显示名称和内部 ID，不返回邮箱、用户名或 Profile 字段，并排除当前成员。创建邀请后只显示一次、7 天有效的 token 链接。加入行程绝不隐含授权；成功后的唯一主要操作是前往授权页。

### 范围化授权 — P0

按用途而非数据库 scope 名称展示字段：旅行偏好、预算护栏、出发/舒适度限制、国籍/入境准备（单独确认）、证件（MVP 不收集或展示）。每项说明使用者（`Shared Trip Agent for this trip`）、原因和产生的能力。撤回时用确认对话框警告“这会使相关方案与确认过期”，并刷新 trip、consent、plan、readiness、confirmation 查询。

### 共享行程工作台与候选比较 — P0

页头显示行程标题、路线/日期、方案版本、`ACTIVE`/`STALE`/`SUPERSEDED` 状态。主体持续呈现成员获准摘要、当前推荐及决策依据、当前用户的下一步/准备事项和可折叠的来源元数据。无有效方案时，明确指出缺失授权或 `UNAVAILABLE` 的供应商数据，并链接到正确恢复步骤。

最多比较三个候选。每个候选展示总价/币种、匹配排序、按出发地的航班、住宿、地面交通、来源与采集时间、报价有效期、可用性/缺失服务，以及仅使用已授权约束的解释。MVP 不提供地图和自由目的地搜索；选中项须有非颜色状态标识和书面取舍说明。

### 准备、重规划、确认与预订沙箱 — P0

准备清单默认只显示当前用户；国籍尚未授权时仅展示核验缺口和授权链接，不能推断或展示国籍。所有不确定结果均指向官方来源，并说明非法律意见或批准。

重规划页并排显示旧/新版本，注明触发因素（价格、库存、出发限制或授权变化），将旧版本保留为只读证据，并按“保留”“变化”“需要你输入”分组。无可行方案时说明阻塞限制，给出对应编辑/授权入口，不能静默放宽偏好。

确认卡只提供 `Confirm this plan` 与 `Needs changes` 两个选择，并显示三位必需成员状态。只有 API 返回当前方案且全员已确认时，预订操作才可用。结果逐服务展示 sandbox 参考号/失败、请求状态和安全重试提示；未标注 sandbox 时，绝不能称为“已预订”。

## 5. 全局状态与无障碍契约

所有路由提供加载、空态、错误和未授权变体。前端以服务端的 `STALE`、授权、确认门槛及预订资格为准；仅可在服务器接受 mutation 后乐观更新显示。

| 场景 | 必需行为 |
|---|---|
| 获取方案/重规划 | 使用带 `aria-busy` 的稳定骨架屏；极快响应不闪烁 spinner。 |
| Mutation 等待 | 禁用发起控件，保留上下文，不移动焦点并播报进度。 |
| 校验错误 | 提交后显示字段内错误和可聚焦的 `role="alert"` 摘要。 |
| 无权访问私密数据 | 显示中性的拒绝访问状态，不透露隐藏数据是否存在。 |
| 供应商缺失/故障 | 显示 `UNAVAILABLE` 缺失服务卡片和恢复操作；不得编造或替代价格、库存。 |
| 签证不确定 | 显示官方核验 CTA、不确定性文字，不使用法律或批准措辞。 |
| 过期方案 | 持续显示版本/状态横幅和 diff/replan 链接；旧确认明确失效。 |

遵循 4/8px 间距尺度、语义化颜色 token、可见键盘焦点、普通文本 4.5:1 对比度、DOM 顺序与视觉顺序一致、`prefers-reduced-motion`，并在 375px、768px、1024px、1440px 验证。

## 6. 推荐前端技术栈（已确认）

浏览器必须调用现有 Fastify REST API；不得通过直连数据库客户端或 Next Server Action 绕过它。

| 关注点 | 推荐 | 原因 |
|---|---|---|
| 框架 | **Next.js 16 App Router + React 19 + TypeScript** | 支持路由布局、流式加载、响应式交付，并匹配 AWS Amplify Hosting。 |
| 样式 | **Tailwind CSS 4 + shadcn/ui + Radix primitives** | 快速、可访问地组合表单、对话框、标签页、折叠区和告警。 |
| 服务端状态 | **TanStack Query v5** | API 是方案/授权/确认的权威；负责请求、缓存、mutation、失效、重试及规划期间短轮询。 |
| 本地 UI 状态 | React state 优先；仅跨路由临时 UI 用 Zustand | 不复制服务端权威业务状态。 |
| 表单 | **React Hook Form + Zod** | 为资料、行程、授权、确认、恢复路径提供类型化渐进表单与可访问校验。 |
| API 客户端 | 基于 Fastify OpenAPI 生成或维护的 typed `fetch` wrapper | 集中处理演示用户 header、错误/关联 ID、响应解析与取消请求。 |
| 图标与日期 | Lucide React；初期使用 `Intl` | 提供一致的可访问 SVG 图标与本地化日期/货币格式，避免过早引入重量级日期库。 |
| 测试 | Vitest + Testing Library + Playwright | 单元/组件、键盘与读屏相关交互，以及预置数据端到端 Hero 流程。 |
| 可观测性 | 隐私审核后再启用 OpenTelemetry 浏览器埋点 | 传播 trace context，且不记录 prompt、国籍、证件或未授权资料字段。 |

### 渲染与数据规则

- 静态 shell/layout 与公开帮助页用 Server Components；交互表单、Agent 输入、授权控制、筛选及 mutation 反馈用 Client Components。
- 使用路由 `loading.tsx` 与局部 `<Suspense>`，避免缓慢的 plan/readiness 请求阻塞整个工作台。
- 对 `POST /consent/*`、`/planning/generate`、`/change-events`、`/confirmations`、`/bookings`，只失效最小相关 Query 集合。
- MVP 不使用 Server Actions 承担领域 mutation；Fastify 已是授权与业务真相边界。未来如用于 Next 自有能力，也须将其当作公开 endpoint 进行校验与授权。

完整的基础设施、后端、Agent 与数据选择记录在 [TECH_STACK.md](../TECH_STACK.md)。

## 7. API 就绪度与缺口

| UI 能力 | 现有 API 覆盖 | 完整实现前的新增需求 |
|---|---|---|
| Profile 读/写/删 | `GET/POST/PUT/DELETE /profiles` | 安全 profile 响应增加字段级来源和更新时间。 |
| 创建/加入/详情行程 | `POST /trips`、`POST /trips/:tripId/join`、`GET /trips/:tripId` | 增加 `GET /trips`，供首页读取当前用户行程、邀请和角色状态。 |
| 授权 | 已有授予、撤回、当前用户读取接口 | mutation 后返回面向用户的过期影响/版本细节。 |
| 候选比较 | 已有生成与最新方案接口 | 确认响应含 2–3 候选、来源/采集时间和旧/新 diff。 |
| 准备事项 | 包含在规划响应中 | 增加按 trip/plan 的当前用户 readiness 读取接口。 |
| 重规划 | 已有 change event 接口 | 返回或公开前后 plan ID 与结构化、授权后的 diff。 |
| 确认 | 已有读/写接口 | 提供成员安全显示名/头像和权威方案生命周期状态。 |
| 预订沙箱 | 已有提交/callback | 增加刷新后的执行状态/结果读取；资格由服务端给出。 |
| 私有 Agent 聊天 | 尚无 API | 仅在存储、脱敏、保留与授权边界获批后设计独立模型/API；非 P0 演示必需。 |
| 活动时间线 | 内部已有审计 | 增加刻意脱敏、成员授权的活动读取模型/API。 |

不得构建假装这些缺口已补齐的 UI。三分钟演示使用 test-only provider doubles；产品 UI 始终以 Fastify API 返回的事实或 `UNAVAILABLE` 为准。

## 8. 交付顺序与验收

1. 建立 Next.js shell、API client、演示用户切换、token、布局及全局状态。
2. 实现首页行动横幅、静态探索地图、四类地点 fixture 及地点详情抽屉；验证地图失败/未加载的可访问回退。
